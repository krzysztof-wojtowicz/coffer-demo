# Working with AI agents (Claude Code)

The repo is set up so several Claude Code agents and people can work in parallel without stepping on each other.

## Pieces
| File | Role |
|---|---|
| `CLAUDE.md` | Short shared context loaded by every agent: layout, commands, hard rules, workflow |
| `openspec/specs/` | What the system does, per capability; the source of truth for tests and reviews |
| `openspec/changes/<name>/` | One planned change: `proposal.md` (why/what), `tasks.md` (who does what, on which files), delta specs |
| `openspec/config.yaml` | Project context and rules injected into OpenSpec artifacts |
| `.claude/agents/` | Five role agents: `implementer`, `tester`, `reviewer`, `docs-writer`, `explorer` |
| `.claude/skills/orchestrate/` | The main-session playbook: spec → parallel build → integrate → review → docs → archive |
| `.claude/skills/openspec-*` | OpenSpec workflows (generated by OpenSpec; refresh with `make openspec-skills`, never plain `openspec update`) |
| `.claude/skills/ponytail/`, `frontend-design/` | Coding style (smallest sufficient change) and UI design guidance |
| `.claude/settings.json` | Allow-list for routine read-only and test commands |

## A typical change
```
user: "add a net-worth chart"
  └─ openspec-propose → openspec/changes/add-net-worth-history/   (user approves)
  └─ orchestrate:
       implementer ─┐ in parallel, disjoint files, own test DB
       tester ──────┘ tests from the spec scenarios only
       integrate: tests → fix rounds via SendMessage (max 2) → make openapi → make check
       reviewer → fixes → docs-writer (if needed)
  └─ openspec-archive-change → specs updated; commit when the user asks
```

## Rules that make parallel work safe
1. **Disjoint files:** `tasks.md` assigns every file to one owner. Shared files (`main.py`, `config.py`, `pl.ts`, `App.tsx`) get exactly one owner per change.
2. **Spec before code:** the implementer and the tester start from the same delta spec, at the same time.
3. **The tester doesn't read the implementation**, so tests don't copy its mistakes. The implementer doesn't edit tests. Disagreements are settled by the spec.
4. **Separate test databases:** `COFFER_TEST_DB=coffer_test_<module>`.
5. **Generated files once:** only the orchestrator runs `make openapi`, after the build.
6. **Migrations in sequence:** changes with Alembic migrations never run in parallel (one head).
7. **One test file per module:** the tester extends `tests/<module>/test_<module>.py` (frontend: the component's `*.test.tsx`) and never creates parallel files.

## Refactors and parked changes
- **Refactor (behaviour unchanged):** no spec delta; up to 3 implementers on disjoint modules; the existing tests are the safety net (no tester); the reviewer checks behaviour is unchanged; the report includes `git diff --stat`.
- **Parked:** `openspec/parked/` holds changes that are on hold (`openspec list` ignores it). Move one back to `openspec/changes/` to resume it.

## Token economy
- `CLAUDE.md` stays short because every agent loads it; details live in specs and changes.
- Reports are ≤ 15 lines without code; the orchestrator doesn't read agents' code when tests pass.
- Continue agents with `SendMessage` instead of respawning them.
- Model by role: opus for review, sonnet for building and docs, haiku for lookups. At most 3 agents at once.
